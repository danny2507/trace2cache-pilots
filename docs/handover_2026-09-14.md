# Trace2Cache handover — 2026-09-14

## Bottom line

The project has demonstrated that a frozen language model can consume a compact,
model-native continuous runtime message in controlled causal probes.  It has **not**
demonstrated that the message carries instance-specific execution semantics for open-ended Python
repair.  Do not claim a program-repair improvement yet.

The current real-code method is a frozen `Qwen/Qwen2.5-Coder-3B-Instruct` receiver plus a
4.73M-parameter role-aware event encoder.  The encoder turns an execution trace into eight
continuous soft-prefix states placed at a named marker in the receiver prompt.  This is soft-state
insertion, not KV-cache injection.

## Latest result: MBPP repair

The official MBPP splits are task-disjoint: train IDs 601--974, validation IDs 511--600, test IDs
11--510.  Mutants and fuzzed inputs are generated automatically from canonical programs; no LLM
data-generation API is required.  Validation traces are shuffled only with a trace from a different
task, so a successful result must depend on the particular runtime evidence.

| Condition | Initial run patch loss / Repair@1 (8) | Contrastive augmented run patch loss / Repair@1 (8) |
| --- | ---: | ---: |
| No runtime evidence | 0.48276 / 1/8 | 0.57602 / 4/8 |
| Text trace | 0.46882 / 5/8 | 0.55831 / 5/8 |
| True latent trace | 0.22887 / 7/8 | 0.25821 / 6/8 |
| Different-task shuffled latent | 0.22906 / 7/8 | 0.25886 / 5/8 |

The augmented run used 768 balanced bundles from 178 train tasks (387 fuzz-derived), 800
microsteps / 200 optimizer updates, gradient accumulation 4, hinge weight 1.0, and margin 0.1.
It peaked at 12.09 GiB GPU memory.  Only one of eight generated validation tasks was repaired by
the true latent but not the shuffled latent.  Seven generated true/shuffled responses were exactly
the same.  The teacher-forced loss gap was 0.00065, far below the requested 0.1 margin.

Interpretation: the adapter learns a powerful generic continuous “repair” prompt, not yet a
per-execution communication channel.  More of the same full-patch contrastive objective is not the
right next experiment.

Full details and earlier diagnostics are in `docs/pilot_results_2026-09-13.md` and the machine-
readable artifacts are in `artifacts/mbpp_repair/`.

## What is already established

- Controlled synthetic causal-path probes: a one-state latent channel reaches `58.0 ± 10.5%`
  macro accuracy on unseen output pairs and longer traces, against `19.6 ± 1.4%` after latent
  message shuffling.  Role and branch interventions reduce it to chance.
- A native state must be inserted into a semantically meaningful prompt position.  Arbitrary
  prefix placement failed; a named marker with `inputs_embeds` works.
- A one-state codebook can carry multiple facts in a frozen receiver, so receiver capacity alone is
  not the bottleneck.
- Raw/full execution traces do not reliably help current repair prompting.  On Refactory and MBPP,
  much of any gain survives shuffled-trace controls, indicating generic format/prompt effects.

## Recommended next experiments, in order

1. **Build same-prompt counterfactual repair pairs.**  Construct pairs with the same visible buggy
   source/public failure but different hidden behavioral evidence and therefore different correct
   patches.  The runtime message must be necessary to choose a target.  This is the cleanest way to
   prevent the generic-prefix shortcut.
2. **Pretrain the trace encoder on semantic probes.**  Before full-patch training, make its eight
   states predict or match runtime facts such as PASS/FAIL, branch taken, return value, last
   definition, and failing source location.  Use a small probe/head or contrastive matching loss;
   then jointly fine-tune with repair loss.  Evaluate true versus shuffled evidence before decoding
   patches.
3. **Run causal ablations.**  Remove event roles, source line, actual/expected values; shuffle
   values with locations held fixed; and swap pass/fail labels.  These distinguish genuine behavior
   encoding from code copying or a static repair prior.
4. **Use three seeds and task-level confidence intervals.**  Report task-cluster bootstrap CIs,
   true-minus-shuffled gaps, exact output agreement, and held-out-test Repair@1.  Do this only after
   the counterfactual gate is passed.
5. **Test external transfer.**  Extend Refactory beyond question 1, then evaluate on DebugBench,
   HumanEvalFix/QuixBugs, and eventually BugsInPy.  Reserve MBPP+ original official test IDs
   11--510 for final extended-test evaluation because MBPP+ overlaps MBPP train IDs.
6. **Only then compare soft states to KV injection.**  KV injection is an interface ablation, not a
   cure for an encoder that has not learned instance-specific semantics.

## Reproduce the latest run

Create the project-local environment as documented in `README.md`.  Neural runs use CUDA/BF16;
the CPU only executes isolated Python programs to collect traces and validate tests.

```bash
PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True .venv/bin/python scripts/run_mbpp_latent_repair.py \
  --steps 800 --gradient-accumulation 4 --max-train-examples 768 \
  --max-eval-examples 36 --generation-examples 8 --max-new-tokens 256 \
  --contrastive-weight 1.0 --contrastive-margin 0.1 \
  --output artifacts/mbpp_repair/contrastive_augmented_seed173.json \
  --checkpoint checkpoints/mbpp_repair/contrastive_augmented_seed173.pt
```

The run needs roughly 12.1 GiB at peak, so verify available GPU memory first.  The frozen Qwen
weights are loaded from the local Hugging Face cache; they are not committed or re-uploaded.

## Claim discipline

Safe current claim: *model-native latent runtime messages have controlled causal-probe evidence,
but direct execution-to-repair semantic generalization remains an open hypothesis.*

Unsafe current claim: *Trace2Cache improves program repair* or *latent evidence beats text on
real repair*.  The shuffled controls do not support either claim yet.
